
보안 검토 결과, 한 AWS CodeBuild 프로젝트가 인증되지 않은 요청(unauthenticated request)을 사용해 Amazon S3 버킷에서 데이터베이스 채우기 스크립트를 다운로드하고 있음이 확인됐다. 보안팀은 이 프로젝트에서 S3 버킷에 대한 인증되지 않은 요청을 허용하지 않는다.

이 문제를 **가장 안전한 방식**으로 바로잡으려면?

**A.** CodeBuild 프로젝트 설정의 AllowedBuckets 섹션에 버킷 이름을 추가한다. AWS CLI를 사용해 DB 채우기 스크립트를 다운로드하도록 빌드 스펙을 업데이트한다.

**B.** S3 버킷 설정을 수정해 HTTPS 기본 인증(basic authentication)을 활성화하고 토큰을 지정한다. cURL로 토큰을 전달해 스크립트를 다운로드하도록 빌드 스펙을 업데이트한다.

**C.** 버킷 정책으로 S3 버킷에서 인증되지 않은 접근을 제거한다. CodeBuild 프로젝트의 서비스 역할(service role)에 Amazon S3 접근 권한을 포함하도록 수정한다. AWS CLI를 사용해 DB 채우기 스크립트를 다운로드한다.

**D.** 버킷 정책으로 S3 버킷에서 인증되지 않은 접근을 제거한다. IAM 액세스 키와 시크릿 액세스 키를 사용해 AWS CLI로 DB 채우기 스크립트를 다운로드한다.


# 해설

정답: C

해설:

핵심은 인증되지 않은 S3 접근을 제거하되 "가장 안전한 방식"으로 인증을 제공하는 것이다. 두 가지를 함께 해야 한다. 먼저 버킷 정책으로 익명(퍼블릭) 접근을 차단하고, 다음으로 CodeBuild가 인증된 요청을 보낼 수 있게 해야 한다. CodeBuild는 실행 시 자신에게 연결된 **서비스 역할**의 자격 증명을 자동으로 사용하므로, 이 역할에 해당 S3 객체에 대한 읽기 권한을 부여하면 AWS CLI가 임시 자격 증명으로 인증된 다운로드를 수행한다. 장기 자격 증명(액세스 키)을 코드나 환경에 저장할 필요가 없어 가장 안전하다. IAM 역할 기반 접근은 AWS의 자격 증명 관리 모범 사례다.

오답 이유:

A. CodeBuild에는 "AllowedBuckets"라는 설정 섹션이 존재하지 않는다. 존재하지 않는 기능을 전제한 함정이며, 인증 문제를 실제로 해결하지도 못한다.

B. S3는 "HTTPS 기본 인증 + 토큰" 방식을 지원하지 않는다. S3 인증은 AWS SigV4 서명(IAM 자격 증명) 기반이지 커스텀 토큰이나 basic auth가 아니다. 서비스 동작을 잘못 이해한 오답이다.

D. 버킷을 잠그는 전반부는 옳지만, IAM 사용자 액세스 키/시크릿 키(장기 자격 증명)를 사용하는 것은 안전성 면에서 열등하다. 키를 저장·주입·교체·유출 관리해야 하는 부담이 생긴다. CodeBuild가 이미 서비스 역할로 임시 자격 증명을 쓸 수 있는데 굳이 장기 키를 도입할 이유가 없어, "가장 안전한 방식"이라는 기준에서 C에 밀린다.
