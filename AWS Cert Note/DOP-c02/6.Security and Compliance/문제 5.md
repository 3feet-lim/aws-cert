
한 이커머스 회사가 새 플랫폼을 호스팅할 곳으로 AWS를 선택했다. 회사의 DevOps 팀은 AWS Control Tower 랜딩 존을 구축하기 시작했다. DevOps 팀은 AWS IAM Identity Center(AWS Single Sign-On)의 자격 증명 저장소(identity store)를 외부 자격 증명 공급자(IdP)로 설정했고 SAML 2.0을 구성했다.

DevOps 팀은 최소 권한 원칙을 적용하는 견고한 권한 모델을 원한다. 이 모델은 팀이 자기 팀 소유의 리소스만 구축·관리할 수 있도록 허용해야 한다.

요구사항을 충족하는 단계의 조합은? (3개 선택)

**A.** 필요한 권한을 포함하는 IAM 정책을 만든다. `aws:PrincipalTag` 조건 키를 포함한다.

**B.** 권한 집합(permission set)을 만든다. 필요한 권한을 포함하고 `aws:PrincipalTag` 조건 키로 권한 범위를 좁히는 인라인 정책을 연결한다.

**C.** IdP에 그룹을 만든다. 사용자를 그룹에 배치한다. IAM Identity Center에서 그룹을 계정과 권한 집합에 할당한다.

**D.** IdP에 그룹을 만든다. 사용자를 그룹에 배치한다. 그룹을 OU와 IAM 정책에 할당한다.

**E.** IAM Identity Center에서 접근 제어용 속성(attributes for access control)을 활성화한다. 사용자에게 태그를 적용한다. 태그를 키-값 쌍으로 매핑한다.

**F.** IAM Identity Center에서 접근 제어용 속성을 활성화한다. IdP의 속성을 키-값 쌍으로 매핑한다.


# 해설

정답: B, C, F

해설:

이 시나리오는 IAM Identity Center + 외부 IdP(SAML) 환경에서 ABAC(속성 기반 접근 제어)로 "각 팀이 자기 리소스만" 관리하도록 최소 권한을 구현하는 전형적 패턴이다. 세 조각이 맞물린다.

F — 외부 IdP를 쓰므로 팀 소속 같은 속성을 IdP에서 가져와야 한다. IAM Identity Center에서 "접근 제어용 속성"을 활성화하고 IdP의 속성(예: 부서/팀)을 SAML 어서션을 통해 키-값 쌍으로 매핑하면, 로그인 시 이 값이 세션 태그(principal tag)로 전달된다. 사용자에게 수동으로 태그를 다는 게 아니라 IdP 속성을 매핑하는 것이 외부 IdP 환경의 정석이다.

B — 권한 부여는 IAM Identity Center의 권한 집합으로 한다. 인라인 정책에 `aws:PrincipalTag` 조건 키를 넣어, 세션에 실린 팀 태그와 리소스 태그가 일치할 때만 작업을 허용하도록 범위를 좁힌다. 이렇게 하면 단일 권한 집합으로 "자기 팀 리소스만" 제어하는 ABAC가 성립해 최소 권한을 만족한다.

C — IdP에 그룹을 만들어 사용자를 넣고, IAM Identity Center에서 그 그룹을 대상 계정과 권한 집합에 할당해 실제 접근을 연결한다. 이것이 IAM Identity Center의 표준 할당 흐름이다.

오답 이유:

A. IAM 정책에 직접 `aws:PrincipalTag`를 넣는 방식은 IAM Identity Center 환경에서 권한을 배포하는 정석 메커니즘이 아니다. Identity Center에서는 정책을 권한 집합으로 감싸 배포하므로(B), 개별 IAM 정책을 만드는 접근은 이 아키텍처와 맞지 않는다.

D. "그룹을 OU와 IAM 정책에 할당"은 잘못됐다. IAM Identity Center에서 그룹은 OU가 아니라 개별 계정에 권한 집합과 함께 할당되며, 할당 대상은 IAM 정책이 아니라 권한 집합이다. 할당 모델 자체가 틀렸다.

E. 접근 제어용 속성을 켜는 전반부는 맞지만, 외부 IdP를 쓰는 이 시나리오에서는 IAM Identity Center에서 사용자에게 수동으로 태그를 적용하는 게 아니라 IdP가 보내는 속성을 매핑해야 한다(F). 수동 태그 관리는 확장성·정합성이 떨어지고 외부 IdP 원천과 어긋난다.
