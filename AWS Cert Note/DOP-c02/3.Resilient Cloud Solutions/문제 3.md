
한 이커머스 회사가 주문 내역 페이지에서 주문 처리 상태 반영이 지연된다는 보고를 받고 있다. 주문 처리 시스템은 예약된 동시성(reserved concurrency)을 사용하는 AWS Lambda 함수로 구성되어 있다. 이 Lambda 함수는 Amazon SQS 큐에서 주문 메시지를 처리하고, 처리된 주문을 Amazon DynamoDB 테이블에 삽입한다. DynamoDB 테이블은 읽기·쓰기 용량에 대해 오토 스케일링이 활성화되어 있다.

이 지연을 해결하기 위해 DevOps 엔지니어가 취해야 할 조치는? (2개 선택)

**A.** SQS 큐의 `ApproximateAgeOfOldestMessage` 메트릭을 확인한다. Lambda 함수의 동시성 한도를 늘린다.

**B.** SQS 큐의 `ApproximateAgeOfOldestMessage` 메트릭을 확인한다. SQS 큐에 리드라이브 정책(redrive policy)을 구성한다.

**C.** SQS 큐의 `NumberOfMessagesSent` 메트릭을 확인한다. SQS 큐의 가시성 제한 시간(visibility timeout)을 늘린다.

**D.** DynamoDB 테이블의 `WriteThrottleEvents` 메트릭을 확인한다. 테이블 스케일링 정책의 최대 쓰기 용량 단위(WCU)를 늘린다.

**E.** Lambda 함수의 `Throttles` 메트릭을 확인한다. Lambda 함수의 타임아웃을 늘린다.



# 해설

정답: A, D

해설:

지연의 원인을 파이프라인의 두 병목 지점에서 각각 찾아 해소하는 문제다. 시스템은 SQS → Lambda → DynamoDB 흐름이고, 처리량을 제한할 수 있는 지점은 (1) Lambda의 소비 속도와 (2) DynamoDB 쓰기 처리량이다.

A — `ApproximateAgeOfOldestMessage`는 큐에서 가장 오래된 메시지가 얼마나 대기했는지를 보여주며, 이 값이 크면 소비 속도가 유입 속도를 못 따라간다는 뜻이다. Lambda가 예약된 동시성으로 제한돼 있으므로 동시 실행 수가 상한에 묶여 메시지가 쌓이는 것이다. 동시성 한도를 늘리면 병렬 처리량이 올라가 큐 적체가 해소된다.

D — 처리된 주문을 DynamoDB에 삽입하는데 쓰기 스로틀이 발생하면 삽입이 지연되고, 이는 곧 주문 상태 반영 지연으로 이어진다. `WriteThrottleEvents`로 쓰기 스로틀을 확인하고, 오토 스케일링 정책의 **최대 WCU 상한**을 올려야 한다. 오토 스케일링이 켜져 있어도 최대 상한에 막히면 더 이상 확장하지 못하므로, 상한 자체를 높이는 것이 정답이다.

오답 이유:

B. `ApproximateAgeOfOldestMessage`로 적체를 확인하는 진단은 맞지만, 리드라이브 정책(DLQ 구성)은 처리 실패 메시지를 데드레터 큐로 보내는 오류 처리 장치다. 처리량 부족으로 인한 지연 자체를 해소하지 못한다.

C. `NumberOfMessagesSent`는 큐로 들어온 메시지 수일 뿐 소비 지연을 진단하는 지표가 아니다. 게다가 가시성 제한 시간을 늘리는 것은 처리 속도를 높이는 것과 무관하며, 오히려 실패 메시지의 재처리를 늦춰 상황을 악화시킬 수 있다.

E. Lambda `Throttles` 메트릭을 보는 것 자체는 유효한 진단이지만, 스로틀의 근본 원인은 예약된 동시성 상한이므로 해결책은 타임아웃 증가가 아니라 동시성 한도 증가(A)다. 타임아웃은 함수 하나의 실행 최대 시간일 뿐 동시 처리량을 늘려주지 않아 적체를 풀지 못한다.
