한 회사가 애플리케이션의 데이터 저장소로 Amazon Aurora 클러스터를 사용하고 있다. 이 Aurora 클러스터는 단일 DB 인스턴스로 구성되어 있다. 애플리케이션은 클러스터의 인스턴스 엔드포인트(instance endpoint)를 사용해 데이터베이스에 읽기·쓰기 작업을 수행한다.

회사는 다가오는 유지보수 기간(maintenance window) 동안 클러스터에 적용할 업데이트를 예약했다. 클러스터는 유지보수 기간 동안 **가능한 한 최소한의 중단**으로 계속 가용 상태를 유지해야 한다.

이 요구사항을 충족하려면 DevOps 엔지니어는 무엇을 해야 하는가?

**A.** Aurora 클러스터에 리더 인스턴스를 추가한다. 쓰기 작업에는 Aurora 클러스터 엔드포인트를 사용하도록 애플리케이션을 업데이트한다. 읽기에는 Aurora 클러스터의 리더 엔드포인트를 사용하도록 업데이트한다.

**B.** Aurora 클러스터에 리더 인스턴스를 추가한다. 클러스터에 커스텀 ANY 엔드포인트를 만든다. 읽기·쓰기 작업 모두에 이 커스텀 ANY 엔드포인트를 사용하도록 애플리케이션을 업데이트한다.

**C.** Aurora 클러스터에서 다중 AZ(Multi-AZ) 옵션을 켠다. 쓰기 작업에는 Aurora 클러스터 엔드포인트를 사용하고, 읽기에는 리더 엔드포인트를 사용하도록 애플리케이션을 업데이트한다.

**D.** Aurora 클러스터에서 다중 AZ 옵션을 켠다. 클러스터에 커스텀 ANY 엔드포인트를 만든다. 읽기·쓰기 작업 모두에 이 커스텀 ANY 엔드포인트를 사용하도록 애플리케이션을 업데이트한다.



# 해설

정답: A

해설:

핵심 제약은 단일 인스턴스 클러스터가 유지보수 중 최소 중단으로 가용성을 유지해야 한다는 점이다. 인스턴스가 하나뿐이면 그 인스턴스에 업데이트가 적용될 때 장애 조치(failover) 대상이 없어 다운타임이 발생한다. 리더 인스턴스를 추가하면 유지보수 중 라이터에 문제가 생겨도 Aurora가 리더를 자동으로 새 라이터로 승격(failover)해 중단을 최소화한다. 이때 애플리케이션은 쓰기에 **클러스터 엔드포인트**(항상 현재 라이터를 가리키며 failover 시 자동으로 새 라이터로 전환됨)를, 읽기에 **리더 엔드포인트**를 사용하도록 나눠야 엔드포인트가 failover를 올바르게 따라간다. 참고로 문제 지문의 "Aurora cluster endpoint"는 곧 라이터를 가리키는 클러스터(=writer) 엔드포인트를 의미한다.

오답 이유:

B. 리더 인스턴스를 추가하는 방향은 맞지만, Aurora의 커스텀 엔드포인트는 읽기 확장/그룹핑 용도이지 읽기·쓰기를 한 엔드포인트로 라우팅해 주지 않는다. 커스텀 엔드포인트에는 라이터를 승격·추적하는 클러스터 엔드포인트의 failover 라우팅 기능이 없어, 이를 쓰기용으로 쓰면 failover 후 쓰기가 올바른 인스턴스로 가지 않을 수 있다. 쓰기는 반드시 클러스터(writer) 엔드포인트를 써야 한다.

C. "Multi-AZ 옵션을 켠다"는 표현은 RDS(MySQL/PostgreSQL 등)의 개념이다. Aurora는 스토리지가 이미 여러 AZ에 복제되는 구조라, 인스턴스 수준의 고가용성은 별도의 "Multi-AZ 토글"이 아니라 다른 AZ에 리더(레플리카)를 추가하는 방식으로 확보한다. Aurora에는 켤 수 있는 그런 옵션이 없어 전제가 틀렸다.

D. C의 잘못된 "Multi-AZ 옵션" 전제와 B의 잘못된 커스텀 ANY 엔�포인트 사용을 동시에 갖고 있어 두 가지 오류가 겹친다. Aurora에 존재하지 않는 옵션을 켠다는 점, 그리고 쓰기를 커스텀 엔드포인트로 라우팅한다는 점 모두 부적절하다.
