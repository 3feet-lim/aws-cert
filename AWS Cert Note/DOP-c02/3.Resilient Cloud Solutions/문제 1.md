
한 회사가 고객에게 애플리케이션을 제공한다. 이 애플리케이션에는 AWS Lambda 함수를 호출하는 Amazon API Gateway REST API가 있다. 초기화 시 Lambda 함수는 Amazon DynamoDB 테이블에서 대량의 데이터를 로드한다. 이 데이터 로드 과정 때문에 콜드 스타트 시간이 8~10초로 길어진다. DynamoDB 테이블에는 DynamoDB Accelerator(DAX)가 구성되어 있다.

고객들은 애플리케이션이 간헐적으로 요청 응답에 오랜 시간이 걸린다고 보고한다. 애플리케이션은 하루 종일 수천 건의 요청을 받는다. 한낮에는 하루 중 다른 어느 때보다 10배 많은 요청이 발생한다. 하루가 끝날 무렵에는 요청량이 평소 총량의 10%로 감소한다.

DevOps 엔지니어는 하루 중 모든 시간대에 Lambda 함수의 지연 시간을 줄여야 한다.

이 요구사항을 충족하는 솔루션은?

**A.** Lambda 함수에 동시성 값 1로 프로비저닝된 동시성(provisioned concurrency)을 구성한다. DynamoDB 테이블의 DAX 클러스터를 삭제한다.

**B.** Lambda 함수에 동시성 값 0으로 예약된 동시성(reserved concurrency)을 구성한다.

**C.** Lambda 함수에 프로비저닝된 동시성을 구성한다. Lambda 함수에 AWS Application Auto Scaling을 구성하여 프로비저닝된 동시성 값을 최소 1, 최대 100으로 설정한다.

**D.** Lambda 함수에 예약된 동시성을 구성한다. API Gateway API에 예약된 동시성 최대값 100으로 AWS Application Auto Scaling을 구성한다.



# 해설

정답: C

해설:

핵심 제약은 "하루 중 모든 시간대에" 지연을 줄여야 한다는 점과, 트래픽이 크게 변동한다는 점(한낮 10배 급증, 저녁 평소의 10%)이다. 콜드 스타트가 8~10초로 긴 원인은 초기화 시 대량 데이터 로드인데, 프로비저닝된 동시성(provisioned concurrency)은 실행 환경을 미리 초기화해 warm 상태로 대기시키므로 콜드 스타트를 제거한다. 다만 트래픽이 시간대별로 10배까지 요동치므로 고정된 프로비저닝 값으로는 부족하다. 따라서 Application Auto Scaling을 붙여 프로비저닝된 동시성을 최소 1~최대 100 범위에서 수요에 따라 자동 조절하면, 급증 시에도 warm 환경이 확보되고 한산할 때는 낮춰 비용도 절약된다. "모든 시간대"라는 요구를 유일하게 충족하는 선택지다.

오답 이유:

A. 프로비저닝된 동시성을 값 1로 고정하면 한낮 10배 급증 구간에서 warm 환경이 턱없이 부족해 대부분의 요청이 여전히 콜드 스타트를 겪는다. 또한 DAX 삭제는 DynamoDB 읽기 지연을 오히려 늘려 데이터 로드를 더 느리게 만들 뿐, 문제 해결과 무관한 함정이다.

B. 예약된 동시성(reserved concurrency)은 함수가 사용할 수 있는 동시성 상한을 지정하는 것이지 실행 환경을 미리 warm하게 만들지 않는다. 게다가 값 0은 함수를 아예 호출 불가 상태로 만들어 애플리케이션을 완전히 중단시킨다. 명백한 오답.

D. 예약된 동시성은 콜드 스타트를 줄이지 못한다(그건 프로비저닝된 동시성의 역할이다). 또한 API Gateway는 Application Auto Scaling으로 "예약된 동시성"을 조절하는 대상이 아니며, Lambda 개념을 API Gateway에 잘못 갖다 붙인 함정이다.
